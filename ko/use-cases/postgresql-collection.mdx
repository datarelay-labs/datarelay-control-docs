# PostgreSQL 테이블의 로그를 수집하기

**목표:** Control의 **Database query (PostgreSQL)** Connector로 테스트 테이블을 읽어 HTTP Destination에 전달합니다. 사용자가 관리하는 **테스트 DB**가 필요합니다.

## 시작 전: PostgreSQL 연동 정보 준비

아래 정보를 먼저 준비해야 Connector와 Stream 설정 도중 중단되지 않습니다.

1. **제품 API/연동 가이드 확인:** host, port, DB/schema/table, read-only SELECT user, SSL certificate, incremental ID/timestamp semantics. Vendor 공식 API 문서에서 실제 Endpoint, 인증 방법, 응답 샘플과 데이터 수집 제한을 확인합니다.
2. **권한·네트워크 확인:** 읽기 전용/최소 권한 계정과 Control 서버에서 Source에 도달하는 네트워크를 준비합니다. 운영 Secret을 문서나 ChatGPT에 붙여넣지 않습니다.
3. **데이터 정의 확인:** 실제 샘플 2~5개(개인정보 제거), 이벤트 배열/필드명, 시간·ID, 페이지 처리와 중복 방지 기준을 정리합니다.
4. **목적지 정보 준비:** 수신 시스템의 IP/URL, Port, Protocol, TLS 및 인증, 정상 수신 확인 방법을 준비합니다.
5. **모르겠다면 ChatGPT 활용:** Vendor API 문서의 공개된 부분과 비식별 샘플을 이용해 필수 Connector 항목·API Request·Record Root·Checkpoint 후보를 정리합니다. **생성된 설정은 공식 문서 및 Run Test로 검증**해야 합니다.

### ChatGPT에 물어볼 예시

> DataRelay Control의 Database query (PostgreSQL) Connector로 로그를 수집하려고 합니다. 아래 공개 API 설명과 비식별 샘플을 기준으로 ① 필요한 인증/접속 정보 ② Request·Pagination ③ Event Root와 주요 필드 ④ Checkpoint 후보와 중복 위험 ⑤ Destination으로 전송하기 전 확인할 사항을 표로 정리해 주세요. 문서에서 확인되지 않은 정보는 추정하지 말고 확인 필요로 표시해 주세요.

## 처음부터 끝까지 따라하기: 공통 작업 순서

1. **Connector 생성:** Connectors → Create Connector → **Database query (PostgreSQL)**. 준비한 정보로 Database host/name/username, SSL mode, read-only query을(를) 입력합니다. 저장 후 제공되는 연결 테스트를 실행합니다.
2. **Destination 생성:** Destinations → Create에서 실제 수신 시스템 유형(SYSLOG_UDP/TCP/TLS 또는 WEBHOOK_POST)을 선택하고 Host/Port/URL/TLS/인증을 설정합니다. 독립 테스트 수신기로 먼저 확인하는 것을 권장합니다.
3. **Stream 생성:** Streams → Create → **Connect**에서 방금 만든 Connector를 선택하고 API/파일/DB 수집 조건을 지정합니다.
4. **Sample & Record Selection:** Run Test로 실제 데이터가 수집되는지 확인합니다. Event Root, 추출 레코드, Union Schema, Checkpoint와 중복 처리 기준을 확인합니다.
5. **Destinations:** 준비한 Destination을 선택하여 Route를 생성합니다.
6. **Route Processing:** Mapping/Transform에서 필드명·시간·추가 필드를 확인합니다. 필요하면 개인정보 **Mask**, **Tokenize**(현재 버전에서 실제 제공되는 경우에만), Remove/Drop, Quarantine/Block을 선택합니다. Route별 Inherit/Override 및 Effective Status를 확인합니다. 보호 기능을 단순히 켰다고 실제 출력이 보호되었다고 가정하지 않습니다.
7. **Deploy 및 실행:** Readiness 경고를 해결하고 저장·배포 후 Stream을 실행합니다.
8. **최종 검증:** query preview, row counts, cursor/tie-breaker and destination receipt. **Run ID, Route Delivery Log, 실제 수신 시스템의 데이터**를 대조합니다.

### 실패·스키마 변경 시

- **접속/인증 실패:** DNS/방화벽/TLS, Token 만료, API 권한, 호출 제한을 확인합니다.
- **수집은 됐으나 레코드 0건:** 응답 Envelope, Record Root, Pagination, 파일 포맷을 다시 확인합니다.
- **전송 실패:** Streams → Routes → Logs 순서로 Run/Route/Destination, Policy, Retry를 조사하고 [전송 장애 가이드](/ko/use-cases/delivery-incident)를 수행합니다.
- **새 필드/타입 변경:** Union Schema의 Observed/Confirmed 상태, Field Path, Unknown Field 정책과 Route Override를 검토하고 [Schema Drift 가이드](/ko/use-cases/schema-change)를 수행합니다.
- **마스킹·토크나이징 미적용:** 실제 버전의 지원 여부, Rule 저장, Effective Status, 최종 Destination Payload를 확인합니다. Preview만으로 성공 처리하지 않습니다.

<Note>
스크린샷은 제품 버전·화면 상태와 출처가 검증된 이미지에만 추가합니다. 현재 인증된 내부 화면의 신규 캡처가 확보되지 않은 단계는 텍스트 절차를 유지하며 가짜 UI 이미지를 사용하지 않습니다.
</Note>


## 1. 테스트 테이블 준비

승인된 테스트 PostgreSQL DB에서 다음 SQL을 실행합니다.

```sql
CREATE TABLE IF NOT EXISTS control_tutorial_events (
    id bigint PRIMARY KEY,
    occurred_at timestamptz NOT NULL,
    message text NOT NULL
);
INSERT INTO control_tutorial_events(id, occurred_at, message)
VALUES (101, '2026-10-18T00:00:00Z', 'synthetic db event')
ON CONFLICT (id) DO NOTHING;
```

별도 읽기 전용 DB 계정을 만들고 테이블에 `SELECT` 권한만 부여합니다. Control 서버에서 DB 포트에 접근 가능해야 합니다.

## 2. Connector 설정

1. **Connectors → Create Connector → Database query (PostgreSQL)**을 선택합니다.
2. **Connector Name** = `Lab PostgreSQL`, **DB type** = `PostgreSQL`을 지정합니다.
3. 실제 **Host**, **Port**(보통 5432), **Database name**, **Username**, **Password**를 입력합니다.
4. 서버 인증서 정책에 맞는 **SSL mode**를 설정합니다. 운영 인증서가 존재한다면 `VERIFY_FULL` 같은 검증 옵션을 사용합니다.
5. 저장하고 지원되는 DB Connectivity Test를 실행해 권한/TLS/네트워크를 확인합니다.

## 3. SQL Query와 Sample 확인

1. `/streams/new`에서 저장한 Connector를 선택합니다.
2. **Connect/Run Test**의 DB Discovery 또는 Query Builder에서 읽기 전용 Query를 구성합니다.

```sql
SELECT id, occurred_at, message
FROM control_tutorial_events
ORDER BY occurred_at, id
```

3. **Run Test**에서 샘플 1건 이상을 확인하고 **Record Selection**에서 반환 레코드를 선택합니다.
4. Union Schema와 필드 타입을 확인합니다.
5. 증분 수집을 사용한다면 안정적인 Cursor/정렬과 ID Tie-breaker를 갖추고 Checkpoint를 명시적으로 검증합니다. 시간 필드가 있다고 자동으로 올바른 Cursor가 되는 것은 아닙니다.

## 4. 전송 확인

1. [테스트 HTTP 수신기](/ko/use-cases/lab-setup)를 `WEBHOOK_POST` Destination으로 선택합니다.
2. **Route Processing**에서 Mapping/Preview를 검토하고 **Deploy**를 수행합니다.
3. Stream을 실행한 후 **Logs**와 `received-9011.ndjson`에서 해당 DB 이벤트를 찾습니다.
4. 추가 가상 Row를 삽입한 뒤 재수집하여 중복이나 누락이 없는지도 검증합니다.

**완료 조건:** DB 테스트 Query 성공, Route 전달 로그, 독립 HTTP 수신 파일에 동일한 이벤트 존재.

## 실패 시

- 연결 실패: DB Host/Port, SSL, 계정 및 권한 확인
- Query 0건: DB/Schema/Table과 WHERE 조건 확인
- 중복/누락: 정렬, Checkpoint와 Tie-breaker 확인
- PostgreSQL이 아닌 DB: 현재 확인된 Query Runtime은 PostgreSQL 중심이므로 추가 엔진 지원을 가정하지 않습니다.

**관련:** [HTTP API 수집](/ko/use-cases/http-api), [Schema 변경](/ko/use-cases/schema-change).
