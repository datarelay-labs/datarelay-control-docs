# HTTP API에서 이벤트 수집하기

**목표:** 제품의 HTTP API Polling Connector로 이벤트를 수집해 일반 Stream/Route를 통해 Destination으로 전송합니다.

## 시작 전: HTTP API 연동 정보 준비

아래 정보를 먼저 준비해야 Connector와 Stream 설정 도중 중단되지 않습니다.

1. **제품 API/연동 가이드 확인:** Base URL, endpoint/method, pagination, rate limits, sample response, API key/OAuth scope and token expiry. Vendor 공식 API 문서에서 실제 Endpoint, 인증 방법, 응답 샘플과 데이터 수집 제한을 확인합니다.
2. **권한·네트워크 확인:** 읽기 전용/최소 권한 계정과 Control 서버에서 Source에 도달하는 네트워크를 준비합니다. 운영 Secret을 문서나 ChatGPT에 붙여넣지 않습니다.
3. **데이터 정의 확인:** 실제 샘플 2~5개(개인정보 제거), 이벤트 배열/필드명, 시간·ID, 페이지 처리와 중복 방지 기준을 정리합니다.
4. **목적지 정보 준비:** 수신 시스템의 IP/URL, Port, Protocol, TLS 및 인증, 정상 수신 확인 방법을 준비합니다.
5. **모르겠다면 ChatGPT 활용:** Vendor API 문서의 공개된 부분과 비식별 샘플을 이용해 필수 Connector 항목·API Request·Record Root·Checkpoint 후보를 정리합니다. **생성된 설정은 공식 문서 및 Run Test로 검증**해야 합니다.

### ChatGPT에 물어볼 예시

> DataRelay Control의 HTTP API Polling Connector로 로그를 수집하려고 합니다. 아래 공개 API 설명과 비식별 샘플을 기준으로 ① 필요한 인증/접속 정보 ② Request·Pagination ③ Event Root와 주요 필드 ④ Checkpoint 후보와 중복 위험 ⑤ Destination으로 전송하기 전 확인할 사항을 표로 정리해 주세요. 문서에서 확인되지 않은 정보는 추정하지 말고 확인 필요로 표시해 주세요.

## 처음부터 끝까지 따라하기: 공통 작업 순서

1. **Connector 생성:** Connectors → Create Connector → **HTTP API Polling**. 준비한 정보로 Host / Base URL, credential/auth mode, request path and parameters을(를) 입력합니다. 저장 후 제공되는 연결 테스트를 실행합니다.
2. **Destination 생성:** Destinations → Create에서 실제 수신 시스템 유형(SYSLOG_UDP/TCP/TLS 또는 WEBHOOK_POST)을 선택하고 Host/Port/URL/TLS/인증을 설정합니다. 독립 테스트 수신기로 먼저 확인하는 것을 권장합니다.
3. **Stream 생성:** Streams → Create → **Connect**에서 방금 만든 Connector를 선택하고 API/파일/DB 수집 조건을 지정합니다.
4. **Sample & Record Selection:** Run Test로 실제 데이터가 수집되는지 확인합니다. Event Root, 추출 레코드, Union Schema, Checkpoint와 중복 처리 기준을 확인합니다.
5. **Destinations:** 준비한 Destination을 선택하여 Route를 생성합니다.
6. **Route Processing:** Mapping/Transform에서 필드명·시간·추가 필드를 확인합니다. 필요하면 개인정보 **Mask**, **Tokenize**(현재 버전에서 실제 제공되는 경우에만), Remove/Drop, Quarantine/Block을 선택합니다. Route별 Inherit/Override 및 Effective Status를 확인합니다. 보호 기능을 단순히 켰다고 실제 출력이 보호되었다고 가정하지 않습니다.
7. **Deploy 및 실행:** Readiness 경고를 해결하고 저장·배포 후 Stream을 실행합니다.
8. **최종 검증:** Run Test HTTP status, JSON record root, cursor/ordering and 401/403/429 troubleshooting. **Run ID, Route Delivery Log, 실제 수신 시스템의 데이터**를 대조합니다.

### 실패·스키마 변경 시

- **접속/인증 실패:** DNS/방화벽/TLS, Token 만료, API 권한, 호출 제한을 확인합니다.
- **수집은 됐으나 레코드 0건:** 응답 Envelope, Record Root, Pagination, 파일 포맷을 다시 확인합니다.
- **전송 실패:** Streams → Routes → Logs 순서로 Run/Route/Destination, Policy, Retry를 조사하고 [전송 장애 가이드](/ko/use-cases/delivery-incident)를 수행합니다.
- **새 필드/타입 변경:** Union Schema의 Observed/Confirmed 상태, Field Path, Unknown Field 정책과 Route Override를 검토하고 [Schema Drift 가이드](/ko/use-cases/schema-change)를 수행합니다.
- **마스킹·토크나이징 미적용:** 실제 버전의 지원 여부, Rule 저장, Effective Status, 최종 Destination Payload를 확인합니다. Preview만으로 성공 처리하지 않습니다.

<Note>
스크린샷은 제품 버전·화면 상태와 출처가 검증된 이미지에만 추가합니다. 현재 인증된 내부 화면의 신규 캡처가 확보되지 않은 단계는 텍스트 절차를 유지하며 가짜 UI 이미지를 사용하지 않습니다.
</Note>


## API 소유자에게 먼저 확보할 정보

실제로 접근 가능한 Base URL, 요청 경로/Method, 인증 방식, 개인정보가 제거된 응답 샘플, Pagination, 이벤트 순서 및 Cursor/Checkpoint 정의가 필요합니다. 아래 주소는 실제로 동작하는 API가 **아닌 설명용**입니다.

| 항목 | 예시 | 설정 위치 |
| --- | --- | --- |
| Base URL | `https://vendor.example.invalid` | Connector의 **Host / Base URL** |
| API 경로 | `/v1/audit/events` | Connect/Run Test의 Request Path |
| 인증 | Vendor 문서상의 API Key 또는 Bearer | Credential/Auth |
| 이벤트 배열 | `$.events` | 실제 응답에서 해당 경로가 존재하는 경우 Record Selection |
| 커서 | `event_time` | 해당 필드가 안정적·단조증가하는 경우만 Checkpoint |

## 1. Connector 만들기

1. **Connectors → Create Connector**로 이동하여 **HTTP API Polling**을 선택합니다.
2. **Connector Name**, 실제 **Host / Base URL**을 입력합니다.
3. Vendor가 지원하는 인증 방식을 선택하고 Credential을 구성합니다. Secret을 공개 YAML이나 샘플 JSON에 넣지 않습니다.
4. Connector를 저장한 뒤 연결 테스트 기능이 제공되면 실제 응답/TLS/권한을 검증합니다.

## 2. 수집 방법 지정

1. `/streams/new`를 열고 **Connect**에서 앞의 Connector를 선택합니다.
2. 실제 Endpoint, HTTP Method, Query Parameter를 설정합니다.
3. Vendor 문서에 따라 Page/Offset/Cursor 방식의 Pagination을 설정합니다. 제품마다 방식이 다르므로 임의로 추정하지 않습니다.
4. **Sample & Record Selection → Run Test**에서 API 호출을 수행하고 HTTP Status와 응답 JSON을 확인합니다.
5. **Record Selection**에서 실제 이벤트 배열을 지정합니다. `{"events":[...]}` 구조가 확인될 때만 `$.events`를 선택하고 추출 건수를 검증합니다.
6. Union Schema에서 필수/드문 필드와 민감 필드 제안을 검토합니다. 자동 제안한 Record Path와 Checkpoint는 사용자 확인 후 사용합니다.
7. 이벤트 진행 상태에 사용할 Checkpoint Mode와 Field를 구성합니다. 안정적인 Cursor가 없는 API라면 잘못된 증분 수집을 강행하지 않습니다.

## 3. Destination 연결 및 배포

1. **Destinations**에서 기존 목적지를 선택합니다. 독립 검증이 필요하면 [테스트 수신기](/ko/use-cases/lab-setup)를 사용합니다.
2. **Route Processing**에서 Transform, 필요한 Data Protection, Preview를 확인합니다.
3. **Deploy**의 차단 경고를 해결한 후 배포하고, 필요 시 Stream을 시작합니다.
4. 실제 수집 Run을 수행하여 **Logs의 Route 결과**와 **Destination 수신 기록**을 모두 확인합니다.

## 4. 증분 수집의 정확도 확인

- Run ID, 수집 이벤트 ID/시간 범위, 실행 전 Checkpoint를 기록합니다.
- 새 이벤트가 없는 상태에서 다음 주기를 실행하고 예상치 못한 중복이 없는지 확인합니다.
- 테스트 가능한 Vendor API라면 새 가상 이벤트를 추가하고 수집·전송·Checkpoint 갱신을 검증합니다.
- **필요한 Destination 전달이 성공하기 전에는 Checkpoint가 전진하지 않아야** 합니다.
- Timestamp 중복/순서 변경이 있는 API라면 커서 전략을 수정해야 합니다.

## 문제 해결

| 증상 | 확인할 항목 |
| --- | --- |
| 401/403 | Credential, Token 만료, Vendor 권한 |
| 429/Timeout | 호출 제한, Backoff, Connector/API Health |
| API 응답은 오지만 레코드가 0건 | JSON Envelope, Event Root, 요청 필터 |
| 동일 이벤트 반복 수집 | Cursor/Checkpoint, 정렬 기준 |
| 수집은 됐으나 전송 실패 | Route, Destination, Policy/Protection, Logs |

**완료 조건:** 신규 이벤트가 독립 Destination에 저장되고, 그 이벤트의 Route 전송 로그와 Checkpoint 동작이 일치합니다.

**관련:** [Schema 변경](/ko/use-cases/schema-change), [전송 장애](/ko/use-cases/delivery-incident).
