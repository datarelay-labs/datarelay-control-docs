# Collect Events from PostgreSQL

**Goal:** use the implemented **Database query (PostgreSQL)** Connector to read a controlled table and send events to an HTTP Destination. This requires a test PostgreSQL database owned by you.

## Before you start: collect PostgreSQL integration requirements

1. **Read the vendor integration/API guide:** obtain host, port, DB/schema/table, read-only SELECT user, SSL certificate, incremental ID/timestamp semantics. Confirm actual endpoint, auth, pagination and limits from official documentation.
2. **Prepare access:** least-privilege credentials, network/TLS access from Control, and a sanitized representative response. Never paste secrets into ChatGPT.
3. **Understand records:** 2–5 redacted examples, event root, timestamps, unique IDs, cursor and duplicate-handling rules.
4. **Prepare the Destination:** actual receiver URL/IP, port, protocol, TLS/auth and independent receipt method.
5. **Ask ChatGPT when uncertain:** provide public vendor documentation and redacted examples; request a checklist of Connector inputs, request/pagination, record root, checkpoint candidates and missing facts. Verify every answer against the vendor guide and Run Test.

### Suggested ChatGPT prompt

> I am configuring DataRelay Control's Database query (PostgreSQL) Connector. Using only the public API documentation and sanitized examples below, identify required connection/authentication fields, requests and pagination, event root, timestamp/ID checkpoint candidates, security considerations and verification. Mark anything not documented as 'needs confirmation'. Do not invent API paths or credentials.

## Follow the complete operator workflow

1. **Create Connector:** Connectors → Create Connector → **Database query (PostgreSQL)**. Enter Database host/name/username, SSL mode, read-only query. Save and run the available connection test.
2. **Create Destination:** Destinations → Create; select SYSLOG_UDP/TCP/TLS or WEBHOOK_POST as appropriate and enter the actual receiver's host/port/URL, TLS and auth. Prefer a controlled test sink first.
3. **Create Stream:** Streams → Create → **Connect**, select the saved Connector and set source request/file/query parameters.
4. **Sample & Record Selection:** Run Test, inspect real records, confirm record root, Union Schema, checkpoint, pagination and deduplication.
5. **Destinations:** select the saved Destination; confirm the corresponding Route exists.
6. **Route Processing:** configure field Mapping/Transform, timestamp normalization and enrichment. For sensitive fields select Mask, Remove/Drop, or **Tokenize only when the deployed version exposes and supports it**; configure Quarantine/Block when appropriate. Verify Inherit/Override and Effective Status, not only a draft preview.
7. **Deploy and run:** resolve readiness errors, deploy and explicitly start/enable the Stream when required.
8. **Prove delivery:** query preview, row counts, cursor/tie-breaker and destination receipt. Match exact Run ID, Route delivery log and independent Destination receipt.

### Troubleshooting and schema drift

- **Connection/auth:** inspect DNS, firewall, TLS, token scope/expiry, 401/403/429 and rate limits.
- **Zero records:** inspect actual response envelope, record root, pagination and source format.
- **Delivery failure:** follow [Delivery incident response](/use-cases/delivery-incident) from Streams → Routes → Logs.
- **New or changed fields:** inspect Union Schema Observed versus Confirmed Drift, unknown-field policy and effective Route override; follow [Schema change](/use-cases/schema-change).
- **Protection not applied:** verify supported Mask/Tokenize action, saved rule, effective status and actual receiver payload. A preview is not proof.

## 1. Prepare the test table

Run the following SQL in an authorized **test** PostgreSQL database using an administrator account:

```sql
CREATE TABLE IF NOT EXISTS control_tutorial_events (
    id bigint PRIMARY KEY,
    occurred_at timestamptz NOT NULL,
    message text NOT NULL
);
INSERT INTO control_tutorial_events(id, occurred_at, message)
VALUES (101, '2026-10-18T00:00:00Z', 'synthetic db event')
ON CONFLICT (id) DO NOTHING;
```

Provision a separate read-only database user with `SELECT` on that table. Configure network access from Control to PostgreSQL; do not use a production write-enabled account.

## 2. Configure the Connector

1. Open **Connectors → Create Connector**, select **Database query (PostgreSQL)**.
2. Enter **Connector Name** = `Lab PostgreSQL`, **DB type** = `PostgreSQL`.
3. Set actual **Host**, **Port** (typically 5432), **Database name**, **Username**, and **Password**; choose your server's correct **SSL mode** (e.g. `VERIFY_FULL` with a valid certificate).
4. Save and execute the supported database connectivity test. Confirm `SELECT` permission and TLS.

## 3. Select and test the query

1. Open `/streams/new`, choose the saved Connector.
2. Use the database discovery/query builder supported by **Connect** and **Run Test**. Use a read-only query like:

```sql
SELECT id, occurred_at, message
FROM control_tutorial_events
ORDER BY occurred_at, id
```

3. Confirm the query actually returns the synthetic row. Set **Record Selection** to the returned record set.
4. Review column types and checkpoint strategy. If incremental mode is required, use the documented stable cursor/tie-breaker field; the sample timestamp alone is not sufficient evidence of monotonicity or uniqueness.
5. Confirm Union Schema and mapped event output.

## 4. Deploy and verify

1. Choose the [lab HTTP sink](/use-cases/lab-setup) as a `WEBHOOK_POST` Destination.
2. In **Route Processing**, review the field mapping/output preview.
3. **Deploy**, start the Stream if needed, and inspect **Logs** and the sink's `received-9011.ndjson`.
4. Add an additional synthetic test row with a greater ID/timestamp using your authorized database account; verify collection behavior and absence of unexpected duplicates.

**PASS:** the authorized read-only query returns the expected row, a Route delivery is recorded, and the sink contains the corresponding event.

## If it fails

- Authentication: check DB host/port/SSL/readonly account.
- Query yields zero rows: inspect database/schema/table selection and timestamp filters.
- Duplicate or omitted rows: inspect event ordering, incremental checkpoint and tie-breaker.
- Database supports something other than PostgreSQL: the documented runtime is PostgreSQL-centric; **do not claim another engine is supported without source/fixture proof**.
