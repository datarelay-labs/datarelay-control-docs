# Hands-on Use Cases

Choose what you want to accomplish. Each guide includes a starting state, numbered actions in the actual Control UI, expected evidence, and recovery steps. The guides are for the development implementation in `datarelay-labs/datarelay-control` **main-v2 @ f7ae7b35 (18 October 2026)**, not a blanket assertion that every feature has passed release or browser acceptance.

<Warning>
Use synthetic events and a non-production environment. Do not paste live tokens, production personally identifiable information, or a private customer's log data into the examples. Actual Control browser E2E is still in progress ([product verification issue #413](https://github.com/datarelay-labs/datarelay-control/issues/413)); a successful preview is not proof of delivery.
</Warning>

**Prefer visuals?** Follow the [numbered Stream Wizard screenshots](/use-cases/screen-walkthrough), from Connector selection to deployment and Logs.

## Connector-first workflow

**① Review the vendor API guide → ② Prepare access/auth/sample data → ③ Ask ChatGPT with public documentation and redacted samples if uncertain → ④ Create and test Connector → ⑤ Create Destination → ⑥ Create Stream and confirm records/checkpoint → ⑦ Mapping, masking and supported tokenization → ⑧ Deploy → ⑨ Verify Logs and real receiver → ⑩ Troubleshoot delivery/schema drift.**

Each Connector guide now starts with its specific inputs, an actionable ChatGPT prompt, the full UI workflow and failure diagnostics. Screenshots must be authentic and version-verified; do not treat placeholders as product evidence.

## Mental model

```text
Source / Connector → Stream → Route A → Destination A
                            └→ Route B → Destination B
```

**Stream** is the execution unit. A **Route** is the destination-specific processing unit; do not duplicate a Stream just to get different outbound transformations. Work in this order: **Connect → Sample & Record Selection → Destinations → Route Processing → Deploy**.

## Evidence checklist for every scenario

- Connection or Source test shows the expected sample or an explicitly recorded limitation.
- Deploy shows readiness; warnings are reviewed, not silently ignored.
- Stream is active and a new run is visible.
- Each expected Route has a matching delivery log and a receiver-side record (when delivery applies).
- A failed, quarantined, or blocked event is **not** counted as successful delivery.
